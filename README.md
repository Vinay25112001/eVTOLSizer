# eVTOL Sizer — Wright State University

A browser-based conceptual sizing tool for electric VTOL aircraft, battery or
turboelectric.
It sizes six layouts (multicopter, side-by-side, lift+cruise, tiltrotor and
two lift/cruise hybrids — "hybrid" there is a rotor layout, not a powertrain)
on NDARC/AFDD-style weight and performance methods, and tags every
output with how far it has been checked: validated, sourced, derived,
calibrated or unverified.

Live site: <https://evtolsizer.live> (deployed from the `main` branch; see
[DEPLOY.md](DEPLOY.md)).

---

## What this tool is, and is not

- **A conceptual-design and teaching tool.** Under NASA's software
  classification (NPR 7150.2D, Appendix D) it is Class E — "parametric models
  to estimate performance or other attributes of design concepts" — for as
  long as it is used to explore concepts. Class E is software "not used to
  make decisions for an operational Class A, B, or C system or a to-be-built
  Class A, B, or C system"; used that way, it needs a higher classification
  (Class D covers engineering design and modeling tools), and the user is
  responsible for the extra assurance that implies.
- **Not a certification tool.** It produces no compliance data. Regulators
  do not approve sizing tools (EASA's proposed CM-S-014 §4.2: the Agency
  "does not approve software tools or programs, but only verifies the
  compliance data generated by these tools"), and DO-178C/DO-330 do not apply.
- **Not independently reviewed.** Its credibility is self-assessed against
  NASA-STD-7009B in [VALIDATION.md](VALIDATION.md), which scores technical
  review at zero for exactly that reason.
- **Two powertrains.** Battery-electric (the pack flies the mission) and
  turboelectric (a turboshaft-generator flies it; the pack is only for an
  engine-out landing), after NASA's reference concepts. The turboelectric
  model has been compared with ONE published aircraft. Parallel hybrids and
  pure turboshaft drive are not modelled.

How well it agrees with published aircraft, and where it does not, is in
[VALIDATION.md](VALIDATION.md). That file is generated from the test
harnesses and CI fails if it goes stale, so it is the place to read numbers
from — this README deliberately quotes none.

## Features

- **Sizing engine** (`src/engine.js`, `src/engine/`): ISA atmosphere, hover,
  climb, cruise, descent and reserve power; component weight build-up;
  iterative gross-weight convergence; wing, tail, stability, load cases,
  battery sizing by energy and power, acoustics, and more.
- **Output provenance** — every output carries its validation status.
- **Design files** — save a design to your account, to local version history,
  or to a `.evtol.json` file (no account needed). A design file stores every
  input, the engine build that produced it and its results; reopening it
  re-runs the design and says whether today's engine still gives the same
  answer.
- **Exports** — CSV, an HTML/PDF report, OpenVSP geometry, CPACS 3.5
  (the mass statement, validated against the CPACS schema) and a
  requirements-traceability CSV.
- **Engine API** — the same engine from Node or the `evtol-size` command,
  with warnings attached to every result; see [docs/API.md](docs/API.md).
- **Accounts and community features** (optional; need a configured Supabase
  project) — registration with name, email, mobile number and password,
  email one-time-code verification via EmailJS, sign-in by email, mobile or
  username; shared designs, a leaderboard, and collaboration sessions.
- **AI assistant** via the Groq API (optional; needs a key).
- **Dark and light themes.**

## Where the engine came from

The engine began as a JavaScript port of a MATLAB sizing script,
`eVTOL_Full_Analysis_v2.m`. It has since been rebuilt around NDARC/AFDD
methods and NASA reference concepts. No validation record of the original
MATLAB script exists in this repository, so nothing here claims one; the
engine's validation is what VALIDATION.md reports.

The default energy reserve is 20 minutes. That value is the FAA powered-lift
SFAR's VFR reserve and NASA's sizing convention (Johnson & Silva 2022). EASA
SC-VTOL VTOL.2430(b)(4) requires a "sufficient reserve" and gives no number.

## Project structure

```
.github/workflows/   verify.yml (all gates, report check, build) and deploy.yml
src/
  api.js             the public Node API (docs/API.md)
  App.jsx            composition root: state, sizing call, tab shell
  engine.js          sizing core and orchestration
  engine/            physics modules (weights, aero, loads, battery, ...)
  lib/               defaults, design files, provenance, theme, persistence
  tabs/ panels/ ui/  interface
  export/            report and OpenVSP exporters
  AuthSystem.jsx     accounts (Supabase + EmailJS)
  CommunityFeatures.jsx  sharing, leaderboard, collaboration
bin/evtol-size.mjs   command-line sizing
validation/          the verification gates run by `npm test`
docs/                API, sizing-loop explainer, validation programme
paper/               conference abstract (numbers checked by a gate)
```

## Local development

Requires Node.js 20 or later.

```bash
git clone https://github.com/Vinay25112001/eVTOLSizer.git
cd eVTOLSizer
npm install
cp .env.example .env     # optional: Supabase, EmailJS and Groq settings
npm run dev              # http://localhost:5173
npm test                 # every verification gate; all must pass
```

The sizing engine needs no keys and runs with an empty `.env`; accounts,
sharing and the AI assistant do not.

## Deployment

Pushing to `main` runs the verification workflow and, only if it passes,
builds and publishes to GitHub Pages. Read the pre-flight list in
[DEPLOY.md](DEPLOY.md) first: the local branch here is `master`.
